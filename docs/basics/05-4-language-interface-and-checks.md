# 05-4 从语言表示到机器人任务接口

经过 05-1～05-3，机器人已经可以把文字变为数值表示，检查指令中的对象和动作，并让整幅图像与整句文字在共同空间中比较。但还缺三个不能混为一谈的问题：**用户要求做什么，画面里哪个对象对应这句话，执行后如何判断要求已经满足**。本节把它们接成一条可检查的任务链，而不在语言编码器上附加它本来没有的能力。

## 给下游什么：句向量、token 表示与任务字段

一条指令经过编码器，可保留 token 级输出 $Z^{\mathrm{lang}}\in\mathbb R^{B\times L\times D}$，也可汇总为整句向量 $z_g\in\mathbb R^{B\times D}$。若下游只需粗略知道“搬运”还是“推动”，整句向量便于使用；若要把“红色杯子”“托盘左边”“不要碰蓝杯”分别指向视觉区域、空间关系和约束，token 表示更有机会保留这些局部细节。05-2 的结构化任务字段还可作为检查清单，不必取代连续特征。

例如“把红杯放到托盘上”可整理为动作“放置”、对象“红杯”、目标“托盘上”。语言编码器给出的是这些条件的**数值表示或可读字段**，并未从相机里测到红杯坐标。视觉模块需要从当前画面找出红杯与托盘，再由第 06 章的深度和坐标变换把图像位置转换成机器人使用的空间目标。第 07 章才会把这个目标同机器人本体与动作接口放在一起。进阶篇的第 09～10 章会进一步讲多种 token 怎样通过 Attention 形成可供动作生成读取的 Context。

~~~mermaid
flowchart LR
    G["用户指令"] --> L["语言表示<br/>对象、目标、约束"]
    O["当前相机观测"] --> V["视觉表示<br/>候选物体与区域"]
    L --> M["图文对应<br/>确定目标区域"]
    V --> M
    M --> P["空间目标与动作接口"]
    P --> X["实际执行"]
    X --> C["重新观测并检查结果"]
~~~

图中语言与视觉两条路径直到“图文对应”才结合，防止把语言向量误当作物体坐标；“实际执行”之后还有重新观测，防止把模型提出的动作误当作任务已经成功。

## 从语言目标到可观测的成功条件

“放到托盘上”描述人的意图，却没有给出唯一的判定规则。一个教学用的具体化方案可以要求：杯子中心位于托盘内部的安全区域，杯子在短时间内保持静止，夹爪已经松开，且搬运途中未碰到禁止触碰的蓝杯。这些条件分别需要位置、连续观测、夹爪状态与碰撞记录支持。若机器人没有相应传感器或记录，就只能说某项条件**尚未验证**，不能因为语言模型复述了“任务完成”便算成功。

同一任务也可能有不同的具体阈值：杯子底部是否必须完全接触托盘，允许多少位置误差，是否要求竖直，都应由任务约定给出。语言编码器负责提供目标线索，不负责自行决定全部物理评测标准。若指令是“把它放那里”，目标对象或位置不明，系统还应先澄清；数值向量可以被算出，不代表命令已足够安全、明确。

## 接入预训练编码器时检查什么

项目可先固定一个已有语言编码器，只训练后续任务模块，检查对象、否定和空间关系能否从特征中读出。若特征不足，再考虑仅调整少量附加参数、解冻部分层，或在数据与算力足够时继续训练整个编码器。调整范围越大，越需要用未见指令与场景检查是否过拟合；“通用文本能力很强”不等于“当前机器人术语与控制约束都已可靠”。

无论哪种方式，都要连同模型记录 tokenizer 词表与版本、特殊 token、最大长度、截断规则、padding mask、输出是整句还是 token 序列。只保存网络权重而更换分词器，相同中文句子就可能变成不同 id；只保存句向量而丢失否定位置，后续模块也无法重新读取那项约束。这些是和第 01 章的动作单位、时间戳同样重要的数据契约。

检验时按 05-2、05-3 的边界逐项设计样本：同义改写是否保持目标，否定词和左右关系改变后输出是否改变；画面中有两个相似杯子时，系统是否定位正确对象；只有一张整图匹配得分时，是否明确报告“尚无目标坐标”；动作执行后，传感器是否支持成功判定。三份 Notebook 分别只覆盖其中的输入、槽位和整图配对环节，没有完成完整机器人闭环。

本章建立了语言进入机器人模型的接口，也指出它不能独自解决的部分。下一章从相机像素出发补上深度、相机内外参和坐标变换：即使“红杯”已经在图像中被找到，机械臂仍需知道它在三维空间的哪里。
